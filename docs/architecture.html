▸ 架構總覽（由上而下，5 層）

此圖依 manuscript-editor 真實程式碼調整層名——它是一個「絕大部分純前端 + 一條可選的動態 API 代理」的 Next.js 應用，不是傳統 Worker／佇列型後端。
① 使用者／瀏覽器 前端頁面 — 單一路由、分頁切換 'use client'
app/page.tsx 是唯一頁面，透過 components/TabNavigation.tsx 切換兩個分頁（無其他 URL 路由，App Router 只有一個 /）：
  • 分頁 A · 字典工具（預設）— 7 項規則式功能勾選、雙欄原文／處理後文字、diff 高亮、統計列
  • 分頁 B · AI 輔助編輯（標示 PRO）— components/AIEditor.tsx，5 家供應商 × 模型選單、API Key 輸入、成本試算
↓
② 前端邏輯層 處理器編排 + 差異計算 + 匯出
lib/textProcessor.ts 依序編排 8 個 processor（比 README 記載的 7 個多一個 removeSpaces.ts）： 簡繁轉換／英文加空白／修正錯字／刪除贅字／修正標點／語義分段／刪除時間戳／移除多餘空白。
另有 lib/diffUtils.ts（diff-match-patch）與 lib/exportUtils.ts（複製／匯出 txt·md）。

▸ Keystone 決定與已驗證的架構張力

KEYSTONE DECISION

純靜態匯出（next.config.ts → output: 'export'）

RPD.md 明文記載理由：免費、無需伺服器、可部署在 GitHub Pages、離線可用、無後端追蹤。7 個規則式功能因此可以完全在瀏覽器端跑，字典即 JSON 靜態資源，這是本專案最初、也是至今仍然生效的核心決定。

後來新增的「AI 輔助編輯」分頁（app/api/ai-process/route.ts）需要一個真正的伺服器來代理呼叫 LLM——這與「純靜態」的 keystone 決定直接衝突。

⚠ 已用實測驗證的矛盾（非臆測）

在本機對這個專案實際執行 npm run build，輸出如下：

Route (app) ┌ ○ / ├ ○ /_not-found └ ƒ /api/ai-process ○ (Static) prerendered as static content ƒ (Dynamic) server-rendered on demand

再檢查 out/ 目錄（GitHub Actions 實際上傳到 GitHub Pages 的內容）：其中沒有 api/ 資料夾 — /api/ai-process 被標記為 Dynamic，靜態匯出時被整條路徑捨棄，build 本身不報錯也不警告。

結論：正式部署站台 https://miku4ocean.github.io/manuscript-editor/ 上，「AI 輔助編輯」分頁按下處理按鈕時，fetch('/api/ai-process') 會打到一個不存在的路徑（404），功能實際不可用。這條路徑只有在 npm run dev 或 npm run start（Node 伺服器模式）下才會真的運作。README / PROJECT_SUMMARY 等文件都未提及此限制。

▸ 資料流（由使用者操作出發）

字典工具分頁：使用者貼上文字 → 勾選功能 → textProcessor.ts 依序呼叫 processors（視需要 fetch 對應字典 json）→ 產出結果 → diffUtils.ts 計算差異 → 畫面顯示高亮 + 統計。全程瀏覽器端執行，無網路需求（首次載入頁面／字典除外）。

AI 輔助編輯分頁：使用者在瀏覽器輸入 API Key（存 localStorage，不上傳伺服器）→ 選 provider/model → 按下處理 → 瀏覽器把 {apiKey, model, text, features} 整包 POST 到 /api/ai-process → route.ts 組 prompt 轉發給對應 LLM → 回應逐次轉發回瀏覽器（不落地儲存文稿或金鑰）→（僅在動態伺服器模式下）畫面顯示 AI 處理結果與成本試算。
